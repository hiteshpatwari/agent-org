# Portable Multi-Agent Engineering Organization V0

## Purpose

Build the smallest serious local implementation of an engineering organization in which a human delegates an objective to a Chief Engineer, a Developer implements it, a Tester independently verifies it, a Reviewer independently reviews it, and the Chief Engineer alone accepts completion. The run must leave a durable ledger, artifacts, reviews, agent-run metadata, and an append-only event log.

## Scope

V0 provides four declarative role definitions, deterministic Chief Engineer workflow logic, a provider-neutral execution protocol, a deterministic MockProvider, one optional OpenAI Responses API adapter, a permission-enforcing local tool registry, filesystem persistence, a CLI, and one executable `sum(a, b)` scenario.

V0 intentionally does not provide autonomous decomposition, general provider routing, MCP execution, distributed workers, peer-to-peer agent chat, sandbox-grade OS isolation, merging, deployment, or production approval policies.

## Assumptions

- Node.js 22 or newer and pnpm are available; the current machine has Node 24 and pnpm 10.
- The repository begins empty and is not a Git repository.
- Ordinary tests and the demonstration must be deterministic and must not call paid APIs.
- The OpenAI adapter is optional at runtime and reads `OPENAI_API_KEY` only through the official SDK; provider types remain inside its adapter module.
- V0 objectives use a declared workflow and workspace template. Deterministic decomposition is an explicit seam, not pretend autonomy.
- Filesystem storage is preferable to SQLite for V0 because the records and append-only log remain directly inspectable, while storage is hidden behind a replaceable port.

## Architecture

Use a pnpm TypeScript workspace with five packages:

- `@agent-org/core`: provider-free schemas, domain entities, state machine, authority rules, provider/tool ports, and invariants.
- `@agent-org/providers`: MockProvider and OpenAIProvider adapters. This package may import provider SDKs; no other package may.
- `@agent-org/tools`: local tool implementations and permission-enforcing registry. Providers receive neutral tool descriptions and never own tools.
- `@agent-org/runtime`: Chief Engineer workflow, agent execution loop, filesystem blackboard, artifacts, event log, configuration loading, and approval gates. It depends only on core ports, never concrete providers or tools.
- `@agent-org/cli`: the composition root. It selects and injects a provider, tool registry, and storage into the runtime.

The enforceable dependency DAG is `core <- providers`, `core <- tools`, `core <- runtime`, and `providers + tools + runtime -> cli`. A boundary test rejects runtime imports of provider SDKs or concrete adapter/tool packages.

The execution protocol is a neutral turn loop. A provider either requests neutral tool calls or returns a structured final value. The runtime executes calls through ToolRegistry, checks the agent's declared permissions, records evidence, and returns tool results to the same provider session. This lets MockProvider and OpenAIProvider use the same orchestration path.

Actor identity is not provider-authored. The runtime creates an immutable `ActorPrincipal` and `ExecutionContext` containing the run, task, agent definition, and role. Provider output contains only the worker payload. The runtime stamps task, agent, run, and role provenance onto results and reviews; conflicting identity fields are rejected. Authorization always receives the trusted principal.

Every tool invocation creates an immutable `ExecutionReceipt` with trusted run/task/agent IDs, exact tool input, fixed working directory where applicable, start/end times, status, bounded output, file hashes, and exit code. Worker payloads cite receipt IDs. Verification must cite an actual passing test-command receipt. Review must cite real diff/read receipts and enumerate acceptance-criterion IDs. Chief acceptance checks those receipts and criterion coverage rather than trusting a success string.

The durable blackboard stores a ledger snapshot plus an append-only JSONL transaction journal. Each line contains one domain event, monotonic revision, previous revision, resulting state hash, and the resulting state. The journal is authoritative and the snapshot is an atomically replaced cache; loading detects gaps/hash mismatches and repairs a stale snapshot from the last valid journal entry. Artifacts contain structured worker results, receipts, verification reports, reviews, and the final report. A run-local workspace is copied from the example template and initialized as a Git repository with a baseline commit, so the demonstration never mutates repository source while still producing a real diff.

## State machine

Task states are:

`PENDING -> READY -> IN_PROGRESS -> VERIFICATION_REQUIRED -> VERIFYING -> REVIEW_REQUIRED -> REVIEWING -> ACCEPTANCE_REQUIRED -> COMPLETED`

Alternate terminal or rework states are `CHANGES_REQUESTED`, `BLOCKED`, `FAILED`, and `CANCELLED`.

Dependencies gate `PENDING -> READY`. A successful Developer result is necessary for `VERIFICATION_REQUIRED`; a Tester pass is necessary for `REVIEW_REQUIRED`; an independent Reviewer approval is necessary for `ACCEPTANCE_REQUIRED`; only the Chief Engineer may perform final acceptance. Changes requested can be reopened by the Chief Engineer.

All mutations go through one command handler/reducer. The principal and guarded transitions are:

| Current | Action | Actor | Guard | Next |
| --- | --- | --- | --- | --- |
| `PENDING` | dependencies satisfied | Chief | every dependency completed | `READY` |
| `READY` | assign/claim | Chief then assigned Developer | declared assignment and role | `IN_PROGRESS` |
| `IN_PROGRESS` | submit implementation | assigned Developer | valid runtime-stamped result with receipts | `VERIFICATION_REQUIRED` |
| `IN_PROGRESS` | fail/block | assigned Developer or Chief | failure/block reason | `FAILED` / `BLOCKED` |
| `VERIFICATION_REQUIRED` | start verification | Chief | independent assigned Tester | `VERIFYING` |
| `VERIFYING` | pass verification | assigned Tester | passing command receipt | `REVIEW_REQUIRED` |
| `VERIFYING` | fail verification | assigned Tester | failing command receipt | `CHANGES_REQUESTED` |
| `REVIEW_REQUIRED` | start review | Chief | reviewer differs from implementer | `REVIEWING` |
| `REVIEWING` | approve | assigned Reviewer | evidence and criterion coverage | `ACCEPTANCE_REQUIRED` |
| `REVIEWING` | request changes | assigned Reviewer | findings | `CHANGES_REQUESTED` |
| `REVIEWING` | block | assigned Reviewer | blocking finding | `BLOCKED` |
| `ACCEPTANCE_REQUIRED` | accept | Chief | passing verification, approval, all criteria covered | `COMPLETED` |
| `ACCEPTANCE_REQUIRED` | reject | Chief | reason | `CHANGES_REQUESTED` |
| `CHANGES_REQUESTED` | reopen | Chief | new/reaffirmed assignment | `READY` |
| non-terminal | cancel/block | Chief | reason | `CANCELLED` / `BLOCKED` |

Implementer, verifier, and reviewer assignments are separate immutable provenance fields, not repeatedly overwritten into one owner field.

Objectives have `PENDING`, `IN_PROGRESS`, `COMPLETED`, `FAILED`, or `CANCELLED` status. Deterministic decomposition returns a validated acyclic task graph. Only the Chief Engineer may complete an objective, and only when every required task is complete with no unresolved blockers or approvals.

## Enforced invariants

- The implementation agent cannot review the task.
- Reviewer and Developer role identities must differ.
- Only authorized roles can perform domain actions.
- Invalid state transitions throw and are not persisted.
- Dependencies must be complete before a task becomes ready.
- Agents can invoke only tools listed in their declarative permissions.
- Tool filesystem paths remain inside the assigned workspace.
- Shell execution is restricted to configured commands.
- Human-gated actions cannot execute without a recorded approval.
- Structured results and reviews are runtime-validated before they affect task state.
- Provider outputs cannot select their own identity or authority.
- Objective completion requires all required tasks to be complete.
- Provider capabilities are declared and checked against workflow requirements before session creation.
- Every agent loop has maximum turns, tool calls, and duration.

## Critical self-review before implementation

1. A package-per-concept layout would create too much ceremony. Five packages preserve the important dependency directions without fragmenting every entity.
2. Calling deterministic code an autonomous Chief Engineer would be misleading. V0 names it a workflow coordinator and makes decomposition replaceable.
3. Letting MockProvider mutate files directly would violate provider/tool separation. The neutral tool-call loop is necessary even in V0.
4. Letting a reviewer merely claim independence in a prompt would be insufficient. Review creation must compare reviewer identity with recorded implementer identity in core.
5. A single mutable ledger would provide state but a weak audit trail. Pairing snapshots with JSONL events gives inspectability without adopting event sourcing.
6. Shell allowlists are not a security sandbox. Documentation must describe them as application-layer least privilege and require stronger isolation for hostile workloads.
7. A real provider should be demonstrably adaptable without making deterministic tests costly. The OpenAI adapter gets contract tests with a fake client and an explicitly gated live smoke test.
8. Provider-authored IDs and claimed evidence are not trustworthy. Runtime provenance, execution receipts, artifact hashes, and acceptance guards establish the evidence chain.
9. Generic shell strings are too permissive. V0 exposes fixed command templates with executable/argv arrays, a fixed real workspace, scrubbed environment, timeouts, and output bounds; no shell interpolation is used.

## Risks and recovery

- Cross-package ESM resolution can fail if packages are not built in dependency order. Workspace dependencies and recursive pnpm scripts will encode the order.
- A failed run may leave partial state. Every meaningful step persists the current snapshot and appends an event; rerunning creates a new run rather than overwriting history.
- Local tool controls do not defend against a malicious executable. V0 constrains paths and command names; a future isolated runner must establish the OS trust boundary.
- Live provider schemas can evolve. OpenAI-specific mapping is isolated and covered by a fake-client contract test.
- Junctions, symlinks, traversal, command-template injection, timeouts, secret redaction, artifact tampering, journal revision mismatch, identity spoofing, loop exhaustion, cyclic dependencies, failed verification, requested changes, and acceptance rejection require explicit negative tests.

## Decisions requiring human input

None for V0. Filesystem persistence, deterministic decomposition, and a scripted demo are reversible choices behind explicit ports.

## Implementation retrospective

V0 met the executable objective without enlarging into a swarm or distributed system. The most consequential architecture-review change was treating provider identity and evidence as untrusted: the runtime now stamps provenance, tools produce receipts, and domain acceptance validates receipt ownership and criterion coverage. A neutral two-turn tool protocol allowed MockProvider and OpenAIProvider to share the same runtime path while keeping concrete adapters out of runtime.

The filesystem blackboard remained appropriate after adding a one-line-per-revision transaction journal. This made recovery and integrity behavior testable without a database dependency. The run-local baseline Git repository solved two competing requirements: the demo produces a real diff, but never edits repository source.

One runtime bug was found by the negative tool tests: a timed-out Windows process returned before releasing its working directory. The command runner now waits for process closure after termination. All deterministic release gates pass. Live OpenAI execution is the sole unverified external path because the configured project has no credits; fake-client contract coverage verifies translation behavior without claiming a successful paid request.
