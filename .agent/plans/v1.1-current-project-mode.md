# V1.1 Current Project Mode

## Purpose and user-visible outcome

V1.1 turns Agent Org into an installable CLI that can be invoked from any clean local Git repository with `agent-org "Implement X"`. The CLI discovers the repository root, converts the prompt into a validated internal Objective, discovers safe Node project commands, creates an isolated Git worktree on an `agent-org/<run-id>` branch, and runs the existing Chief Engineer, Developer, Tester, Reviewer, and acceptance workflow without changing the user's active working tree.

## Scope and non-goals

In scope are prompt and explicit `run` forms, Git-root discovery from nested directories, global and optional project configuration, explicit configuration precedence, deterministic project identity and global run state, prompt-to-objective construction, bounded project context discovery, template and local-Git workspace sources, dirty-tree rejection, Node package-manager and script discovery, installable CLI metadata, integration coverage, and documentation. Existing YAML/template/eval workflows remain supported.

V1.1 does not add providers, arbitrary shell execution, non-Node command discovery, automatic merge, deployment, a dashboard, distributed execution, or direct writes to the user's active worktree.

## Assumptions and constraints

- Node 22+, Git, and one of pnpm/npm/yarn are available to the CLI.
- Normal project mode requires a Git worktree with no tracked or untracked changes. No `--allow-dirty` behavior is introduced.
- Project command execution remains a fixed command-ID catalog assembled by the CLI; the provider cannot provide command strings.
- Environment variables remain the only credential input. Global or project YAML must not contain API keys.
- Repository instructions are untrusted project guidance subordinate to organization security and authority policy.
- Runtime state defaults to the OS-appropriate Agent Org home and can be relocated with `AGENT_ORG_HOME`.

## Current repository state

V1 already has strict Objective records, provider-neutral ports, role-separated execution, fixed command tools, copied template workspaces, append-only journals, resume, evidence freshness, independent review, mock evals, and an OpenAI adapter. The CLI currently equates `process.cwd()` with the Agent Org source/configuration/target/state roots, requires objective YAML, registers fixture command IDs directly, and stages only copied templates. The README contains one uncommitted credential-documentation edit that must be preserved.

## Architecture and package-boundary decisions

`core` adds provider-free workspace source metadata and a WorkspaceSource port. Objective remains the validated internal representation; its existing `workspaceTemplate` field remains readable for V1 journals and fixture YAML.

`runtime` adds project discovery/configuration, global defaults, deterministic project state identity, bounded context discovery, package-manager and fixed-command discovery, and an ObjectiveBuilder. It receives an explicit workspace source and no longer needs one overloaded repository root for staging. Configuration resolution models `agentOrgHome`, `projectRoot`, and `runtimeStateRoot` separately. Precedence is CLI over `.agent-org.yaml` over global configuration over built-in defaults.

`tools` implements `TemplateWorkspaceSource` and `LocalGitWorkspaceSource`. The latter rejects dirty repositories, creates a branch and linked worktree, and returns durable source/branch/path metadata. The existing workspace manager remains the canonical workspace-state inspector during this compatible migration.

`cli` remains the composition root. It resolves source-installation assets only for legacy fixtures, discovers the target Git repository for prompt mode, selects global/project configuration, builds a safe command catalog, constructs the Objective, and injects the workspace source. Query/resume commands resolve the same deterministic project state location without provider credentials.

## Domain invariants and security boundaries

- Project mode never modifies, stages, commits, merges, or cleans the active working tree.
- A dirty repository fails before a run is created or worktree is added; uncommitted changes are never silently copied.
- Worktree source metadata is durable and included in completion output.
- Models can invoke only neutral tool names and configured command IDs. Discovered scripts are limited to the allowlist `test`, `lint`, `typecheck`, and `build` and map to `project.*` IDs.
- Package manager selection prefers a valid `packageManager` declaration, then pnpm, yarn, and npm lockfiles in that order.
- Context discovery is bounded to known root guidance/metadata files and explicitly excludes secrets, Git internals, credentials, private keys, and registry credentials.
- Project `AGENTS.md` is labeled guidance and cannot override organization authority, permissions, evidence gates, or secret controls.
- Resume uses the existing workspace and configuration snapshot and cannot restage or merge work.
- Existing template objectives, deterministic provider behavior, journals, evals, authorization, and evidence semantics remain valid.

## Risks, recovery strategy, and unresolved decisions

- Git worktree creation can leave an administrative entry after interruption. Creation uses a unique branch/run path and fails closed; explicit cleanup in tests removes the worktree through Git before deleting repositories.
- Global defaults duplicate stable organization definitions in code. They are schema-validated and global YAML can replace them; a future packaged-assets design may remove the duplication.
- A project may define scripts that execute unsafe native code. Discovery is intentionally narrow and visible, but application policy is not an OS sandbox. This limitation remains documented.
- Existing run lookup is project-scoped. Cross-project run discovery is deferred; operators can set `AGENT_ORG_HOME` or invoke inspection from the originating project.
- Prompt-derived requirements are conservative because Objective must exist before Chief planning. The builder creates one explicit requirement and acceptance criterion from the user's prompt; Chief planning enriches the execution task after bounded repository context is available.

Recovery keeps existing append-only journals authoritative. Before workspace staging failures, no active tree is changed. After staging, resume reuses the same worktree and stage. No automatic worktree removal or branch deletion occurs on success because those artifacts are the user's review handoff.

## Final implementation retrospective

V1.1 delivered the current-project architecture as an extension of V1 rather than a rewrite. The key design repair was replacing the overloaded repository root with explicit project/global-state/workspace concepts and a provider-neutral WorkspaceSource. Template objectives still create copied baseline repositories, while normal project prompts use clean-HEAD linked worktrees and persist their branch and source metadata. The Objective remains the validated internal contract; prompt conversion supplies conservative runtime-owned fields and lets the existing Chief planning turn refine the task without gaining provenance or authority.

The fixed-command boundary survived project discovery. Node scripts are detected through declared package-manager/lockfile precedence, mapped to four neutral `project.*` IDs, and executed only through trusted command templates. Windows required a deliberate fixed `cmd.exe` wrapper because package-manager `.cmd` shims cannot use the existing shell-free spawn path; script names are narrowly validated and providers still never supply command strings. This remains application policy, not an OS sandbox.

The implementation followed the planned global/project configuration precedence. Built-in organization definitions enable a zero-scaffold first run; optional global organization files and `project-defaults.yaml` remain separate from small `.agent-org.yaml` project settings. Runtime state no longer pollutes normal target repositories. The local installation procedure changed from the initially preferred pnpm global link to `npm link` because this machine has no configured pnpm global bin directory; the shipped root bin was validated directly.

Deterministic acceptance is complete and preserves all V1 modes and invariants. The exact live user workflow was invoked once and reached OpenAI, but API billing rejected it before planning with exhausted credits. Per the user's explicit instruction, no additional live calls were made. Deterministic project mode completed the same workflow with MockProvider, including diff, tests, independent review, and final report. The resume comparison is now canonical and no longer rejects semantically identical snapshots due to serialization details. Consequently the implementation is architecturally ready for V2 provider work, but live-provider acceptance remains conditional on a future operator-run smoke test after billing is restored. V2 itself was not implemented.
